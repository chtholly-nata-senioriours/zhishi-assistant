## 关键结论（对架构的影响）

### 1. 不需要为 AI 调用拆子进程（ADR-4 / ADR-7 确认）

即使 Markdown **每个 token 全量重排**（最重策略），200 tokens 流式下的最大主线程阻塞也只有 **33ms**，  
远低于 50ms 的卡顿阈值。这说明：

- `QTextDocument.setMarkdown()` 可以直接用，**不需要**自绘增量渲染；
- AI 调用可以留在**主进程**，不必拆子进程（音频链路仍建议独立，见 §3.3 公理 A4）。

> 但注意：`setMarkdown` 是 O(n) 全量重排，总成本 O(n²)。本次测到 200 tokens 仍安全；  
> 若未来单次回答超过 ~2000 tokens，需重新评估（可改为节流渲染，如每 80ms 重排一次）。

### 2. 面板必须预热 —— 冷构建 63ms 会吃掉一半延迟预算

冷构建 63ms vs 预热唤起 5.8ms，**差 10 倍**。  
这直接验证了执行框架 §8.2 的设计：面板必须在启动期（`on_ui_ready`）构建好并隐藏待命，  
**绝不能**在热键回调里首次创建。

### 3. `SetForegroundWindow` 必须配 `AttachThreadInput`

直接调用会因 Windows 前台锁静默失败。实现见 `s3_panel.py` 的 `ForegroundGuard`：  
把当前线程 attach 到目标窗口线程后再设置前台窗口，实测还原成功率 100%。

### 4. `time.sleep()` 会阻塞 Qt 事件循环 —— 这是个真实踩到的坑

S2 首轮失败的原因：等待 Ctrl+C 生效时用了 `time.sleep(0.18)`，导致本进程内的目标窗口  
**无法处理 WM_COPY 消息**。改为「泵事件循环 + 短睡眠」后通过。

→ 写进开发规范：**任何等待都不得用裸 `time.sleep()` 阻塞主线程**。

### 5. 依赖装在两个目录 —— 环境引导必须同时挂载

实测发现 `requests`/`Crypto`/`urllib3` 在 `Lib/`，而 `PySide6`/`pynput`/`pywin32` 在  
`Lib/site-packages/`。`dev_bootstrap.py` 已同时挂载两者。

## S5 结果（SSE 中文编码，P2.4）

**症状**：真机接上硅基流动后，划词翻译返回 `ç¿»è¯ç»æ...`。

这是 **UTF-8 字节按 ISO-8859-1 解码**的特征（「翻译」2 字 → 6 字符，长度翻倍）。  
根因是 provider 里的 `resp.iter_lines(decode_unicode=True)`：服务端返回  
`text/event-stream` **不带 charset** 时，requests 按 RFC 2616 对 `text/*` 回退到  
**ISO-8859-1**。

**为什么前四轮验证都没抓到（本仓库最重要的一条教训）**

| 验证      | 为什么漏掉                                                   |
| ------- | ------------------------------------------------------- |
| M1 / M2 | 用**进程内假 Provider**，完全绕过 `OpenAICompatProvider.stream()` |
| S4      | 唯一走真 HTTP 的，但假服务写了 `charset=utf-8` → 解码正确               |
| M3      | 不带 charset，但只断言「请求打到哪个服务」，不看内容                          |
| 单元测试    | 只喂 `str` 给 `iter_openai_deltas`，**编码边界不在被测范围内**         |

**一句话**：测试替身恰好绕过了唯一有问题的那层。

**S5 怎么做**：起一个假服务，**同一个中文样本跑两遍** ——  
一遍 `Content-Type: text/event-stream`（真实服务形态），一遍带 `charset=utf-8`，  
断言 `provider.stream()` 拼出的文本都与原文逐字相等。修复前后对比：

| 响应头                                | 修复前              | 修复后  |
| ---------------------------------- | ---------------- | ---- |
| `text/event-stream`（无 charset）     | ❌ 乱码，29 字 → 60 字 | ✅ 一致 |
| `text/event-stream; charset=utf-8` | ✅ 一致             | ✅ 一致 |

修复后 `decode_lines()` 取**原始字节**自己按 UTF-8 解（SSE 规范固定 UTF-8）。  
按字节切行是安全的：UTF-8 多字节序列的每个字节都在 0x80–0xFF，不含 `0x0A` / `0x0D`。

回归守卫：`tests/test_ai_core.py` 里新增 3 条**集成**用例，  
把「`SessionManager` + 真实 `OpenAICompatProvider` + 真 HTTP（无 charset）」这个组合锁住。

## S6 结果（窗口生命周期，P2.6）

**症状**：关掉「AI 服务设置」对话框，**整个应用退出**。

根因是 `QApplication.quitOnLastWindowClosed` 默认为 **True**，而本项目两个
**常驻**窗口（`PetWindow` / `AIPanel`）都带 `Qt.Tool` 标志 ——
**Tool 窗口不计入「最后窗口」判定**。于是关掉任意普通 `QDialog`，Qt 就认为
「没有窗口了」直接 quit。全仓库没有任何一处调用过 `setQuitOnLastWindowClosed`。

**踩的坑（第一版探针把假设误判成「未复现」）**

`lastWindowClosed` **只在事件循环运行期间才会发出**（Qt 内部有 `in_exec` 守卫）。
第一版探针没调 `app.exec()`，于是永远收不到信号 → 假阴性。而且
`QApplication` 不能销毁重建、`quitOnLastWindowClosed` 是全局状态 ——
所以**每个用例必须单开一个子进程**。

改写后的做法：`--case <name>` 一个子进程跑一个用例，每个都真跑 `app.exec()`，
`QTimer.singleShot(80, dlg.close)` 模拟用户点关闭，500ms 后探活并输出 JSON。

| 用例 | `quitOnLastWindowClosed` | 有常驻 Tool 窗口 | 期望 | 实测 |
|---|---|---|---|---|
| `tool-default` | True（默认） | 是 | **退出**（复现 bug） | ✅ survived=False |
| `tool-fixed` | False | 是 | 存活 | ✅ survived=True |
| `plain-default` | True | 否 | 存活（印证是 Tool 的问题） | ✅ survived=True |

修复：`UIManager.initialize()` 里 `setQuitOnLastWindowClosed(False)`；
退出只能由显式 `app.quit()` 触发（托盘 / 右键菜单「退出」）。

## S8 结果（UI 设计系统，P2.7）

> S7（P2.6 的 UI 统一性探针）已随设计系统重构**失效并删除** ——

**背景**：P2.6 把「各窗口颜色不统一」修成「都走 `GlassTheme`」，但设计语言

| 断言组 | 内容 |
|---|---|
| 颜色收敛 | `qss.py` 零 hex 字面量；UI 代码无「内联样式表写死颜色」 |
| 尺寸规格 | 圆角 2px / 按钮 3px；间距全在 4px 栅格；行高 28px；滚动条 8→12px；图标 16px |

产物：`spikes/results/ui_design/*.png`（16 张：控制中心 4 页 × 2 主题 +
AI 面板 + 设置对话框 + 提示框 + 番茄钟）。

> ⚠ 渲染预览图**不能用** `QT_QPA_PLATFORM=offscreen` —— 那个平台下拿不到
> 中文字形，渲染出来全是豆腐块（`□`）。必须用真实平台。
>
> ⚠ **渲染前必须调 `install(app)`**（P2.14 新增的坑，S13 踩过）。
> `set_theme()` 只对**已注册**的 QApplication 重装 QSS / 字体
> （`theme._reapply` 遍历 `_installed_apps`），而注册动作在 `install(app)` 里。
> 只调 `set_theme()` 不调 `install()` → **QSS 与字体从来没装上**：
> 中文豆腐块 + 所有背景色丢失（看起来像「控件没写样式」）。
> 另一个易混点：`QWidget.render()` 对**没 `show()` 过**的控件拿到的是
> 「没上过样式」的样子 —— QSS 背景是在 `show()` 的 polish 阶段套上去的，

**S8 顺带定位的四个真 bug**（都有回归用例，见 `tests/test_design.py`）：

1. `ThemeToggleButton` 无限递归 —— `refresh_theme` 调 `set_icon`，而
   `IconButton.set_icon` 又回调 `refresh_theme`。
2. `.QWidget` 设了背景色 → 卡片内部的普通 QWidget 容器被染成窗口底色，
   浅色主题下白色卡片里冒出一条条灰带。
3. `#iconButtonDanger` 缺基础规则 → 退化匹配通用 `QPushButton`，
   面板关闭按钮变成 **120×30 的灰块**。
4. 滚动条「hover 变宽」的实现口径（轨道固定 + handle 收 margin，
   避免 hover 时 viewport 重排导致正文抖动）。

**反向验证**：把 `.QWidget` 背景加回去，新用例确实失败。
> 第一版断言只匹配「行首的 `.QWidget`」，被
> `QMainWindow, QDialog, .QWidget { background: ... }` 这种逗号列表绕过去了 ——
> 改成扫整条选择器列表才真正生效。**这本身就是一条教训：
> 反向验证能暴露「写了个永远不会失败的断言」。**

1. **图表底色与页面底色同色** → 时间轴看着像「只画到 2/3 就断了」，

2. **跨天伪切换** → 「昨天收工在浏览器、今天开工写代码」被算成一次应用切换，

   假数据里 08:00 桶不为零（而假数据根本没有早上开工时的切换）就是这么暴露的。

   `switch_count` / `hour_switches` / 摘要共用一处判据。

3. **趋势页两个口径混着算** → 页面向插件要的是 `days * 2` 天

4. **`AxisLabels` 换刻度时旧标签重影** → `deleteLater()` 只是**排队**删除，

**反向验证时踩到的两个「假测试」**（比 bug 本身更值得记）：

1. 先写的断言是「未填的那段要暗到看不见」。**前提本身是错的** ——
   深色任务栏上白描边在未填段本来就该可见（那是它的职责）。
   反向验证当场打红（实测差值 140），说明我在给一个视觉判断硬套像素指标。
   改成断言**「环不随应用主题变」**（逐像素比对），守的是结构性根因。
2. 主题断言最初只测「进行中」态，于是「关闭态读主题」这个 mutation

> ⚠ **「专注中」和「专注计时中」是两件事，别混**：
> 前者是**活动态**（今天的深度工作时间正在进行，环画的是**今日进度**）；
> 后者是**番茄钟态**（用户点了一次「专注」，环画的是**这一轮**的进度）。
> 两者视觉上都是琥珀色，但读的是**不同的量** ——
> 这正是 P2.18 把状态判定收进 `ring_view()` 单一入口的原因（见 `AGENTS.md` §4.13 ③）。

> **按「壁纸底色」分张，不是按应用主题** —— 判据同 S14：
> **这个图标的背景由谁决定？不是应用就別问主题。** 球的底色是壁纸。
> 气泡例外：它走全局 QSS，底色由应用给，所以那两张**按应用主题**分。

**结论**

- **七态在四种壁纸上都分得清。** 环画在**球体上**（不是壁纸上），
  所以环的可读性由球体保证、与壁纸无关；壁纸只影响球体轮廓 ——
  深色壁纸上靠**白描边**站住（球体填充 `#1C1C1C` α205 在 `#141414` 上几乎不可分）。
- **「未采集」的环比「0%」亮**（α120 vs α58；叠在球体上约 128 vs 76）。
  这是**刻意**的（「没在记录」要比「今天没干」显眼），与托盘同一个约定；
  「已达成」是绿色，不会与灰环混。
  ⚠ 但值得记一笔：在 52px 的球上比 16px 的托盘更容易被误读成「满环」。
  若要再改，方向是让关闭态画**虚线环**而不是更亮的实线环（属设计决策，未改）。
- **P2.18 的专注两态**：计时中为琥珀 `#FFB04C` + `clock` 图标；
  暂停为同色 α110（压暗）+ `pause` 图标 —— **颜色与图标两个通道同时区分**，
  不会只靠亮度（亮度差在小尺寸上容易读不出来）。
- 气泡中文正常（不是豆腐块），QSS 背景在，深浅两种壁纸上都读得清。
- 贴边三态符合预期，`edge_snap_inset() = 21px`。

> ⚠ **S15 自己也踩了两个坑**（都已修，但值得记）：
> ① 画布高度只留 40px，放不下末尾的「瞬时态」行 —— 整行被裁在画布外；
> ② 贴边图画布宽 720 放不下第 4 格，桌宠对比图**静默没画出来**
> （`if left + panel_w <= width` 直接跳过，不报错）。
> **教训：目检图「少了一格」不会报错 —— 看图时要数格子，不能只看「有没有图」。**

> **S15 的盲区（重要）**：目检只看**静止的一帧**，所以它**测不出「球在动」**。
> 「数值动画把球拽来拽去」是后来跑 `exe_window_check.py` 枚举窗口才发现的
> —— 多次采样位置一直在跳。**静态目检与动态行为是两把不同的尺子，不能互相替代。**
> 详见 `AGENTS.md` §4.11 ④。

## S9 结果（性能收尾 R14 / R15，P2.8）

**背景**：`docs/执行框架.md` 里挂着两条遗留风险。

| 风险 | 症状 | 根因 |
|---|---|---|
| **R14** | `get_selected()` 双峰 253ms / 565ms | 253ms 峰 = **固定等待**；565ms 峰 = **`clip.clear()` 的跨进程代价** |
| **R15** | `to_png_bytes()` 阻塞主线程 73–136ms | PNG 编码本身慢 |

### R14 第一半 —— 固定等待 → 轮询

旧实现发完 Ctrl+C 后无条件 `_wait(max(delay, timeout_ms))`，即便目标应用
20ms 就写好了剪贴板，也照样等满 250ms。

改为「**30ms 最小响应窗口 + 8ms 轮询**」，一读到内容立刻返回。
没有选中文本的应用根本不会写剪贴板，于是自然走到超时分支返回空串。

`_wait()` 的步进同时从 5ms 压到 2ms —— 否则 8ms 的轮询间隔会被拖成 10ms+。

| 实现 | 耗时（假目标应用 25ms 写好剪贴板） |
|---|---|
| 旧：固定等待 | 250.7 ms |
| 新：轮询 | **32.1 ms** |

### R14 第二半 —— 不再 `clear()` 剪贴板（改用序列号判据）

旧实现靠 `QClipboard.clear()` 制造「空剪贴板」基准，再判断 Ctrl+C 有没有写进东西。
但**清空剪贴板要等前一个所有者进程响应**（Windows 跨进程剪贴板所有权协商）。

改用 `GetClipboardSequenceNumber()`（Win32，纯读、不需要打开剪贴板）判断
「是否发生了新的一次复制」，**完全不清空剪贴板**。

| 操作 | 代价 |
|---|---|
| `clipboard_sequence()` 读取 | **0.001–0.004 ms**（200 次共 0.6–1.5ms） |
| `clip.clear()`（本进程持有剪贴板） | 0.5 ms |
| `clip.clear()`（剪贴板有外部写入者） | **330 ms** |

用户剪贴板里放的通常就是别的应用刚复制的内容，所以这 330ms 是**常态**而非偶发。

> ⚠ **`clear()` 的代价只有跨进程才看得见 —— S9 复现不出来**
> S9 全程在单进程里跑，剪贴板由本进程（Qt）持有，`clear()` 只要 0.5ms。
> 实测直接测 `clear()` 会得到「才 0.5ms，改它干嘛」的错误结论。
> 这就是 S10 存在的原因。
>
> 顺带记一条踩坑：想用「独立助手进程直接写剪贴板」来稳定复现这个 330ms
> **不成立** —— 助手进程写完（数据完好、格式齐全）后 `clear()` 仍只要 0.1ms。
> 能复现的只有「真实应用真的执行了一次复制」。
> 更迷惑的是：一个**只 `EmptyClipboard` 不写数据**的助手进程反而能复现出 330ms。
> 也就是说**慢的根源是所有权交接，与内容无关**，但触发时机依赖外部应用的真实行为，
> 无法用合成手段稳定构造。

### R15 —— PNG → JPEG

多模态上传默认改走 JPEG（质量 88），PNG 路径保留（`fmt="PNG"`）。

| 图源 | PNG | JPEG | 提速 | 体积 |
|---|---|---|---|---|
| 全屏 2560×1600 | 1944 ms / 6212 KB | **98 ms / 894 KB** | 20× | 1/7 |
| 半分辨率 1280×800 | 501 ms / 1761 KB | **23 ms / 306 KB** | 22× | 1/6 |

> ⚠ **差点写进错误结论的坑**
> 第一版 S9 用「纯色 + 规则网格」的合成图对比，结果 PNG 只有 9KB、**比 JPEG 还小** ——
> 得出「JPEG 体积更大」的相反结论。合成图对 PNG 极其友好，**必须用真实屏幕截图**。
> S9 已改为优先真实抓屏，headless 时才回退合成图（并在输出里标注图源）。
>
> 同类陷阱在 `docs/执行框架.md` 的 P2.4 章节也出现过一次（测试替身恰好绕过了有问题的层）。

**反向验证**（每条都确认过断言不是空的）：
- 把 `_poll_clipboard` 改回固定等待 → 新用例失败（实测 252ms）
- 把 `UPLOAD_FORMAT` 改回 `"PNG"` → mime 断言失败
- 让 `clipboard_sequence()` 恒返回常量 → `test_clipboard_sequence_moves_on_real_copy` 失败
- 让测试假件的「版本号」永不递增 → `test_get_selected_returns_as_soon_as_content_appears` 失败

## S11 结果（投递语义：REPLACE ≠ PASTE，P2.9）

**背景**：`DeliveryKind` 里 `REPLACE` 的注释是「替换原文（覆盖选中区）」，
但实现上 `paste_to_foreground()` **根本没有投递方式这个参数** ——
REPLACE 与 PASTE 都只是「写剪贴板 + Ctrl+V」，行为完全一样：

- 选区还在时，**PASTE 也会把原文替换掉**（本该插入）
- 选区丢了时，**REPLACE 退化成插入**（本该替换）

用户看到的是「点了替换原文，原文还在」。

**修法**：区别只在**粘贴前有没有取消选区**。
`replace` 不动选区（Ctrl+V 覆盖它）；`paste` 先按一下 `Right` 取消选区
（有选区时 Right 只取消选中、不移动光标），再粘贴 → 结果插在选区末尾。

### 真实记事本实测

基准 `"AAA BBB CCC"`，先选中 `"AAA"`（`EM_SETSEL 0,3`），投递 `"XXX"`：

| 模式 | REPLACE | PASTE | 判定 |
|---|---|---|---|
| **正常** | `'XXX BBB CCC'` | `'AAAXXX BBB CCC'` | ✅ PASS（两臂不同） |
| **`--legacy`** | `'XXX BBB CCC'` | `'XXX BBB CCC'` | ✅ PASS（两臂相同 → **证明改造前确实未分离**） |

`--legacy` 是**探针自证**：让它模拟改造前的行为（两臂都保持选区），
此时期望「两臂相同」。跑得出来，才说明这个探针真的能区分好坏。

### 顺带测出的第二个缺陷：成功判定恒真

`_send_paste()` 返回注解是 `None` 且吞掉异常，于是 `paste_to_foreground()`
**只在设置剪贴板失败时才返回 False** —— 调用方的「粘贴失败」提示**永远不可达**。

实测：让 pynput 构造抛异常，`paste_to_foreground()` 仍返回 `True`。
现在 `_send_paste()` 如实返回，且**失败时不再白等 120ms**。

### 投递路径的代价分解（2026-10-12 实测）

| 段 | 本进程持有剪贴板 | 外部进程持有 |
|---|---|---|
| `backup()` | 0.2 ms | 0.8 ms |
| `set_clipboard()` | 1.4 ms | **113.1 ms**（首次 464ms） |
| `_send_paste()` | 3–8 ms | 3.4 ms |
| `_pump()` | **123.7 ms** | 121.7 ms |
| `restore()` | 1.0 ms | 0.8 ms |
| **合计** | **134.7 ms** | **240.8 ms** |

两条值得记：

- **`restore()` 并不慢** —— 一旦 `set_clipboard()` 成功，所有权已在本进程，
  还原只是本进程内的写（0.8–1.0ms）。慢的是**第一次** `set_clipboard()`，
  与 R14 同源（跨进程剪贴板所有权交接）。
- **`_pump()` 的 120ms 是有语义必要的固定等待** —— 剪贴板是延迟渲染的，
  目标应用响应 Ctrl+V 时才来要数据；提前还原会粘到旧内容。
  但它只在**粘贴确实发出后**才需要，所以失败时跳过。

### 为什么用窗口消息而不是全局按键注入

> ⚠ **2026-10-12 更正**：本节原来写的是「本机会话里合成按键（pynput /
> SendInput）**落不下去**，是桌面会话状态问题」。**这个说法不准确** ——
> S12 实测：`SendInput` 在沙箱内外**都返回 2/2（接受）**，真按键注入也确实
> 成功过。真相不是「不 work」，而是「**时灵时不灵**」（成功率约 40–50%）。
> 详见下面的 **S12** 一节。

S11 之所以改用窗口消息，是为了**确定性** —— 它要验的是语义（有没有取消选区
→ 结果文本差异），用一个 40% 会失败的通道去验语义，结论就没意义了。
所以这个选择是对的，只是当时给的理由错了。

> ⚠ **诚实标注**：S11 验证的是**语义**（有没有取消选区 → 结果文本差异）。
> 真实按键序列本身由 `tests/test_injector.py` 覆盖 —— 那里断言
> 「Right 出现在 Ctrl+V 之前」「两种 kind 的按键序列不同」。

### 踩过的坑（每一个都真实发生过）

1. Windows 11 新版记事本的编辑控件是 **`RichEditD2DPT`**，不是经典 `Edit`。
2. 消息必须发给**编辑控件**；发给主窗口只会改到**标题栏**（第一次跑就踩了）。
3. 记事本是**单实例**：`notepad.exe` 把文件交给已有实例后自己退出，
   所以 `Popen().pid` **不是** UI 进程 → 用「操作前后窗口集合差集」定位。
4. 必须确认目标窗口打开的是**本次的临时文件**（标题含文件名），
   否则可能动到用户的文档 —— 探针里有这条安全阀。

**反向验证**（4 条，全部确认断言不是空的）：
- 忽略 `clear_selection` → `test_two_kinds_produce_different_key_sequences` 失败
- `_send_paste` 异常也返回 True → `test_paste_returns_false_when_injection_fails` 失败
- 失败后仍无条件 pump → `test_paste_skips_pump_when_injection_fails` 失败
- 插件层恒不取消选区 → `test_paste_delivery_clears_selection_when_context_present` 失败

## S12 结果（真实按键注入**成功率**，P2.11）

### 为什么要有这个 spike

用户反馈「**替换原文和粘贴到前台没有反应**」。在动手删之前先证伪了两件事：

| 假设 | 实测 |
|---|---|
| P2.9 引入了回归 | `tests/test_injector.py` 全绿；M2 端到端投递 **PASS** → ❌ |
| 目标换成**外部应用**才坏 | 专门写探针：真记事本 + 真面板 + 真 `_on_delivery` → `'敏捷的棕色狐狸跃过懒惰的狗。 jumps over the lazy dog.'` → ❌ |

都不是。于是转向「**成功率**」这个此前没人量过的维度。

### 实测：约 40%

真 pynput → 真记事本，同一个探针连跑 10 次：

```
FPPFFPFFFP      →  PASS=4  FAIL=6
```

失败与成功**交错**出现 —— 不是「跑一阵就坏」的状态漂移，是随机的。

抓到的失败形态之一（很有信息量）：

```
基准 "AAA BBB CCC"，选中 "AAA"，剪贴板 "XXX"
  期望 "XXX BBB CCC"
  实得 "v BBB CCC"     ← 字母 v 落下了，**Ctrl 没生效**
```

### `SendInput` 返回值探测：沙箱不是原因

pynput **不检查** `SendInput` 的返回值，所以「没生效」时看不出是被拦了还是
目标窗口不对。S12 直接发一个无副作用的 `VK_F24` 并读返回值：

| 环境 | 返回值 |
|---|---|
| 沙箱内 | **2/2 接受** |
| 沙箱外 | **2/2 接受** |

> ⚠ 写这个探测时踩过一个坑：`INPUT` 结构体的联合体**只声明 `KEYBDINPUT`
> 会让 `sizeof` 少 8 字节**（x64 上决定大小的是 `MOUSEINPUT`），
> `SendInput` 直接报 `ERROR_INVALID_PARAMETER(87)` —— 和「被系统拦掉」
> 长得一模一样，极易误判。现在探针里有 `sizeof` 断言兜底。

### 试过但**没用**的两个修复假设

| 假设 | 实验 | 结果 |
|---|---|---|
| 120ms 后还原剪贴板太早，目标读到旧内容 | 交错对照 6 次：`restore` 1P/2F、`--no-restore` 2P/1F | **无相关** |
| `press(Ctrl)` 与 `press("v")` 之间缺间隔 | 插 40ms 后连跑 5 次 | **5 次全 FAIL**，更糟 |

### 结论：移除

问题不在「能不能做到」，而在「**做不到可靠，且代码察觉不到失败**」：

```python
ok = self._send_paste(...)     # 系统把按键丢掉时不抛异常 → 返回 True
if ok:
    self._panel.set_status("已替换原文")   # ← 谎报成功
```

用户看到的就是「点了没反应」。**一个会谎报成功、时灵时不灵的功能，
比没有这个功能更糟** —— 它让人以为是自己操作错了。

→ P2.11 移除了这两个按钮，只保留「复制」（`AGENTS.md` §4.6）。
`native/injector.py` **保留未删**：它是这件事唯一的实测记录，恢复只需在
`_on_delivery()` 加回两个分支 —— 但**第一步必须是可验证的成功判定**
（注入后回读目标窗口内容），而不是继续猜延迟。

**用法**：
```bash
python dev_bootstrap.py spikes/s12_real_injection.py              # 单次（概率性）
python dev_bootstrap.py spikes/s12_real_injection.py --no-restore # 隔离还原时序
python dev_bootstrap.py spikes/s12_real_injection.py --key-delay  # 隔离按键间隔
# 要看结论请连跑多次统计成功率：
for i in $(seq 10); do python dev_bootstrap.py spikes/s12_real_injection.py | grep 判定; done
```

## 真实 API 自检（P2.0，`api_check.py`）

前面所有脚本都用**假 Provider**，所以「配置对不对」一直没人回答。  
`api_check.py` 补上这一环 —— 它是**唯一会发真实网络请求**的脚本：

| 步骤               | 检查什么                                             |
| ---------------- | ------------------------------------------------ |
| 1. 配置完整性         | `base_url` / `model` / `api_key` 是否齐备（Key 会打码显示） |

## 验证夹具方法论（重要，踩坑记录）

端到端脚本最初**间歇性失败**（10 次错 2–3 次），排查后确认**全是夹具问题，不是产品缺陷**。  
三条必须遵守的规则：

1. **剔除夹具开销**：合成按键的 `SendInput` 阻塞调用线程，pynput 首次构造还要 71ms。  
   不剔除则"最大阻塞"恒等于按键耗时。
2. **剔除设计内等待**：`get_selected()` 内部有刻意的 ~250ms 等待（等目标应用落剪贴板）。  
   这是设计，不是阻塞。
3. **夹具也必须用 `AttachThreadInput` 抢前台**：Windows 前台锁会让 `activateWindow()`  
   **静默失败**，目标窗口抢不到焦点 → `Ctrl+C` 取不到内容 →「替换原文」粘错窗口。  
   复用产品自己的 `ForegroundGuard.restore()`（见 `_common.py::force_foreground()`）。

实现：`Heartbeat.mark_harness(t0, t1)` 标记时间窗，统计时跳过与之重叠的心跳间隔，  
被剔除的部分单独作为数据报告。

> 教训：**端到端脚本失败要先怀疑夹具。** 把"夹具开销"和"设计内等待"显式建模后，  
> 8/8 稳定通过，测出的数字（17ms）才真正反映产品行为。

## 发版核查（每次打包后）

打完包、生成发布包之后跑这三个脚本（P2.13 起固化为正式 spike，之前每次临时重写）：

```bash
PYTHONPATH="Lib;Lib/site-packages;Lib/packtools" \
    python dev_bootstrap.py spikes/pyz_check.py
python dev_bootstrap.py spikes/leak_check.py
python dev_bootstrap.py spikes/exe_window_check.py
python dev_bootstrap.py spikes/smoke_exe.py        # 存活 + 版本行 + 启动序列
```

**P2.16 起再加一道：跑完全量测试后比对用户数据目录**（见上面「用户数据目录比对」一节）——
必须报 `新增 0 / 删除 0 / mtime 变 0 / 内容变 0`。

| 脚本                   | 查什么                                    | 期望                   |
| -------------------- | -------------------------------------- | -------------------- |
| `pyz_check.py`       | PYZ 里的模块 / 符号 / 字符串；旧字面量是否**真走掉**       | `RESULT: PASS`       |
| `leak_check.py`      | 用户真实密钥是否混进发布目录 / zip（**zip 逐条目解压**）     | `RESULT: PASS`（0 命中） |
| `exe_window_check.py` | exe 真的把**可见窗口**画出来了吗（P2.16 新增）          | `RESULT: PASS`       |
| `smoke_exe.py`       | 存活 ≥16s + 版本行 == `config.default.json` + 完整启动序列（P2.19 新增） | `SMOKE: PASS` |
| `userdir_diff.py`    | 跑测试是否动了用户的 `~/.pet_demo/`（P2.16 新增；**须在桌宠未运行时跑**）      | `RESULT: OK`（四项全 0）  |

> **为什么把冒烟做成脚本（P2.19）**：以前每次发版现场拼 Bash 一行流，每次都踩同样的两个坑 ——
> `BEFORE=$(wc -l < log) && ./exe &` 会把整条链丢进子 shell（`BEFORE` 是空的）、
> 列表推导里写错变量名让 `taskkill` **静默没执行**（exe 一直挂着）。
> 另外**版本行在 `stderr` 不在 `stdout`**（`StreamHandler` 默认 stderr）——
> v1.5.0 时的记录写成 stdout，不够准。脚本两个流都收。
> ⚠ 它**证明不了窗口存在**（`app.log` 到「热键已注册」就停，之后进 Qt 事件循环），
> 窗口仍归 `exe_window_check.py` 管，两者都要跑。

`pyz_check.py` 的检查清单在**文件顶部常量**里，发新版按本次改动**追加**（旧项不删，那是回归护栏）。

> ⚠ **P2.18 踩到的坑：字符串检查只覆盖 `EXTRA_MODULES` 里列的模块。**
> 加了一条 `"QProgressBar#focusBar[paused"` 却报 FAIL —— 因为那个字符串只出现在
> `presentation/design/qss.py`，而 `qss.py` 不在符号收集清单里。
> **判据：想查哪个模块的字符串，就得先把它加进 `EXTRA_MODULES`**（`REQUIRED_SYMBOLS` 只看 `engine.activity*` + 清单内模块）。
>
> ⚠ **冒烟判据里的「版本: x.y.z」在 `stdout`，不在 `app.log`。**
> `app.log` 从「AI 助手插件已加载」开始记；版本行是
> `INFO:data.config_manager:加载用户配置成功 (版本: 1.5.0)`，走控制台。
> 所以冒烟要**同时**看 exe 的 stdout 重定向文件与 `app.log`，只看 `app.log` 会以为「版本行没了」。
>
> ⚠ **`Alt+Q` 被占用是环境问题，不是回归**（P2.18 遇到）：三个热键由**同一个循环**注册，
> `alt+t` / `alt+s` 成功而 `alt+q` 失败 ⇒ 不是应用内重复注册。用探针确认：
> `user32.RegisterHotKey(NULL, id, MOD_ALT, VK_Q)` 返回 0 且 `GetLastError()==1409`
> （`ERROR_HOTKEY_ALREADY_REGISTERED`）⇒ 机器上别的程序占着。
> **别急着改代码**；应用会降级为 WARNING 并提示「可从托盘菜单唤起」。

> **为什么需要 `exe_window_check.py`（P2.16 踩出来的）**：
> `app.log` 到「热键已注册」就没了（之后进 Qt 事件循环，不再打日志）——
> **「启动序列完整」证明不了窗口存在**，而 P2.16 改的恰恰是窗口。
> 必须直接问 Windows 枚举 pid 名下的可见顶层窗口。
> 它同时也是发现「动画把球拽来拽去」的那把尺子（见 §4.11 ④）。

> 三个已知坑（写脚本时踩过，改脚本前先看）：
> 1. `extract()` 默认返回 **code object**，不是 bytes（`raw=True` 才给 bytes）；
> 2. 关键字参数名在 **`KW_NAMES` 元组常量**里，必须递归进容器才收得到；
> 3. 「该在的」字符串可能被优化进模块级**大字符串**（如 `_SCHEMA` 里的表名），
>    所以要用**子串**判断；「不该在的」必须用**精确常量**判断（子串会误报）。
>
> 另：zip 打包后若想确认「用户下载的包是否干净」，注意发布**目录**里会混入
> `_internal/engine/**/__pycache__/*.pyc`（spec 的 `datas=('engine','engine')` 一并带入），
> 但 `_refresh_release.py` 打 zip 时**已排除** `__pycache__` 与 `.pyc`，所以 zip 是干净的。
