### 1.5 已识别的宿主缺陷（全部经源码验证）

> 这四条是后续所有设计的前提。**T1–T4 就是为修它们而设**（见 §5）。

**C1 — 插件加载无包上下文（高危）**
`plugin_manager.py:43`：
```python
spec = importlib.util.spec_from_file_location(f"_plugin_{name}", str(plugin_file))
```
模块名为 `_plugin_<name>`，**没有包层级**，因此 `plugin.py` 内不能写 `from .foo import bar`。
`giwifi` 的规避方式是 `sys.path.insert(0, plugin_dir)` + 平级绝对导入，其注释自承风险：
*"logger/config 为插件私有名，加载时优先命中"*。
→ **AI 插件必然有十余个模块，沿用此模式会与其他插件互相污染。**

**C2 — `on_load` 早于 UI 创建（中危）**
`main.py:184` 插件加载 → `main.py:189` `_start_ui()`。`on_load` 执行时
`app.ui_manager.window` 尚为 `None`。
→ **AI 面板必须懒创建或经 `on_ui_ready` 预热**，否则无法满足"低延迟唤起"。

**C3 — EventBus 是同步串行调用（高危）**
`event_bus.py:165`：
```python
for callback in callbacks:      # ← 同步循环
    try:
        callback(event)
```
而 `publish` 的 docstring 写着 *"订阅者在独立线程中执行以避免阻塞发布者"* —— **实现与文档不符**。
发布者通常是 pynput 监听线程或状态机线程。
→ **任何在事件回调里同步发 HTTP 的写法都会直接冻结感知层。这是红线。**

**C4 — 打包依赖手工维护（中危）**
`PetDemo.spec:15` 的 `hiddenimports` 需人工逐条添加（已为 giwifi 手列 8 项 `Crypto.*`）。
且 `PetDemo.spec:65` `console=False`，插件内 `print` 输出会丢失。
→ **每新增一个第三方依赖都要改 spec，漏配只在打包后暴露。**

**附带发现（好消息）**：`event_bus.py:37` 的 `ALLOWED_EVENTS` 白名单中**已预留**
`USER_INPUT`（64 行）与 `AI_REPLY`（65 行）—— 原作者本就规划了 AI 接入，只是未落地。

**其他不一致（低危，记录备查）**：
- `config.default.json` 的 `version` 是 `1.0.0`，CHANGELOG 已到 v1.1.0。
- `presentation/assets/models/default/` 缺 `pet.jpg`（`check_project.py` 会告警）。
  不影响运行 —— `main.py:273` 会播放 `idle` 精灵图覆盖显示。
- `.gitignore` 忽略了 `*.spec`，但 `PetDemo.spec` 是打包必需文件（当前已存在于工作区）。

## 2. 需求与目标

### 2.1 需求原文（用户口径）

> 功能性应当大于陪伴性，桌宠的表现形式并不重要，重要的是它应当具有能够随时被唤起，给我进行查询翻译等功能，像 AI0x0 一样。

### 2.2 需求解读：这是一次定位反转

| 维度 | 改造前 | **改造后** |
|---|---|---|
| 产品本体 | 陪伴型桌宠，AI 是它的能力 | **AI 命令层，桌宠是它的皮肤** |
| 主入口 | 桌宠右键菜单 | **全局热键 + 悬浮面板** |
| 桌宠角色 | 差异化资产，必须承载交互 | **可替换、可关闭的视觉反馈** |
| 价值度量 | 陪伴感 | **唤起速度 / 上下文获取 / 答案投递** |
| 桌宠隐藏时 | 产品失去意义 | **功能完全不受影响** |

### 2.3 硬约束与可量化指标

| 约束 | 含义 | 指标 |
|---|---|---|
| **随时可唤起** | 任何应用、任何时刻，热键必须生效 | 唤起成功率 ≥ 99%；P95 延迟 ≤ 150ms |
| **查询 / 翻译** | 选中即查、选中即译是主力场景 | 选中文本获取成功率 ≥ 95%（主流应用） |
| **不打扰** | 回答完能回到原应用，不丢焦点 | 关闭面板后前台窗口 100% 还原 |

### 2.4 唯一的验收判据

> **把桌宠窗口彻底隐藏，产品是否仍然完整可用？**
> 改造前答案是否；改造后**必须是"是"**。这条判据贯穿全文，是架构决策的最终裁判。

## 3. 第一性原理

### 3.1 "随时可唤起的查询工具"的不可约本质

剥离所有 UI 与外观，只剩四件事：

```
① 可触达 (Reachability)   —— 任何时刻、任何前台应用下都能触发
② 知上下文 (Context)      —— 知道你在看什么 / 选中了什么
③ 能推理 (Inference)      —— 调模型得到答案
④ 可投递 (Delivery)       —— 把答案送回手边，且不打断你
```

**桌宠不在这四件事里的任何一件里。** 桌宠是"系统状态的一种渲染"，与功能正交。

- **推论 A**：陪伴性是表现层问题，功能性是管线问题，两者可彻底解耦。
- **推论 B**：既然解耦，AI 核心就**不得依赖任何桌宠窗口 / 动画 API**。这直接决定模块边界。

### 3.2 功能归约：一切 AI 功能都是三元组

把两个对标产品的全部功能（合计 40+ 项）再降一维，会发现**每个具体功能都只是三个正交维度的取值组合**：

```
功能  ≡  输入源(InputSource) × 预设(Preset) × 投递(Delivery)
```

| 维度 | 取值 |
|---|---|
| **输入源** | 选中文本 / 剪贴板 / 截图 / 手输 / 音频 / 文件 |
| **预设** | 自由问答 / 翻译 / 摘要 / 解释 / 改写 / 代码 / 自定义 |
| **投递** | 面板显示 / 复制 / 替换原文 / 粘贴到前台 / TTS 播报 |

**验证这条归约：**

| 产品功能 | 输入源 | 预设 | 投递 |
|---|---|---|---|
| 划词查询 | 选中文本 | 自由问答 | 面板显示 |
| 划词翻译 | 选中文本 | 翻译 | **替换原文** |
| 截图识图 | 截图 | 自由问答 | 面板显示 |
| 自动键入 | 选中文本 | 自由问答 | **粘贴到前台** |
| Ask 问答 | 手输 | 自由问答 | 面板显示 |
| 会议字幕 | 音频 | 转录 | 面板显示 |

→ **推论 C（本框架最重要的结构性结论）**：不需要为每个功能写一套代码。
只需实现"输入源采集器 / 预设 / 投递器"三组可组合零件，**功能就是配置**。
这把"功能数量"从**代码量问题**降维成**配置量问题**。

### 3.3 设计公理（不可违反）

| # | 公理 | 直接推论 |
|---|---|---|
| **A1** | **功能与外观正交** | AI 核心零依赖桌宠；桌宠隐藏时功能完整（§2.4 判据） |
| **A2** | **感知延迟即产品** | 面板**先出**（≤150ms），上下文**后到**；绝不让用户等采集 |
| **A3** | **功能 = 三元组** | 新增功能不写新流程，只加零件 / 加配置 |
| **A4** | **主线程神圣不可阻塞** | 一切网络 / IO 走线程池；流式渲染不得掉帧（C3 红线） |
| **A5** | **焦点是别人的** | 面板用完必须归还前台焦点；提供"非激活"展示模式 |
| **A6** | **底座复用宿主，代理纯增量** | 常驻进程 / 事件总线 / 配置 / 打包直接复用；系统级 I/O 是全新代码 |

> 与可行性研究 v1 的兼容性：v1 的"宿主 vs 代理""工程量错配（AI 占 20%、系统 I/O 占 80%）"
> "同进程 GIL 上限"三条公理**继续有效**；v1 的"人格是资产""桌宠即 AI 化身"两条**已被本版推翻**。

### 4.3 分层归属规则（防止架构腐化）

| 规则 | 说明 |

**改法**：`extensions/plugin_manager.py`，替换 `_import_plugin_class`（37–52 行）的加载逻辑：

```python
import sys
import types
import importlib.util

_PKG = "petdemo_plugins"
sys.modules.setdefault(_PKG, types.ModuleType(_PKG))


def _import_plugin_class(plugin_dir: Path, name: str):
    plugin_file = plugin_dir / "plugin.py"
    if not plugin_file.exists():
        return None

    full = f"{_PKG}.{name}"
    spec = importlib.util.spec_from_file_location(
        full,
        str(plugin_file),
        submodule_search_locations=[str(plugin_dir)],   # ← 关键：提供包搜索路径
    )
    if not spec or not spec.loader:
        return None
    module = importlib.util.module_from_spec(spec)
    sys.modules[full] = module      # ← 必须先注册，相对导入才能解析
    spec.loader.exec_module(module)

    for _, cls in inspect.getmembers(module, inspect.isclass):
        if issubclass(cls, BasePlugin) and cls != BasePlugin:
            return cls
    return None
```

**为什么这样改**：根因是 `spec_from_file_location` 只加载单文件、不建立包。

### T2 — EventBus 支持异步投递（修复 C3）

**改法**：`event_bus.py` 新增 `publish_async()`，**保留同步 `publish()` 不动**（兼容）。

```python
from concurrent.futures import ThreadPoolExecutor
import threading

_executor = ThreadPoolExecutor(max_workers=4, thread_name_prefix="ebus")


class EventBus:
    # ... 既有代码不变 ...

    def publish_async(self, event_type: str, data: Any = None) -> Dict:
        """异步投递：回调在线程池执行，绝不阻塞发布者。

        用于 AI 请求等耗时操作；高频感知事件仍用同步 publish()。
        """
        if event_type not in ALLOWED_EVENTS:
            logger.warning(f"发布未注册的事件类型: {event_type}")
            self._stats["dropped_count"] += 1

        event = {"type": event_type, "data": data or {}, "timestamp": time.time()}
        with self._lock:
            callbacks = list(self._subscribers.get(event_type, []))
            self._stats["published_count"] += 1

        for cb in callbacks:
            _executor.submit(self._safe_call, cb, event, event_type)
        return event

    @staticmethod
    def _safe_call(cb, event, event_type):
        try:
            cb(event)
        except Exception as e:
            logger.error(f"事件处理异常 [{event_type}]: {e}", exc_info=True)
```

## 8. 目标交互模型

### 8.1 三个主力模式

| 模式 | 默认热键 | 流程 | 投递选项 |
|---|---|---|---|
| **Ask 问答** | `Alt+Q` | 热键 → 面板输入框 → 流式回答 | 复制 / 插入到前台 |
| **Translate 划词翻译** | `Alt+T` | 选中 → 热键 → 面板直接出译文 | **替换原文** / 复制 |
| **Capture 截图问答** | `Alt+S` | 热键 → 全屏选区 → 多模态回答 | 复制 / 面板追问 |

> 三个模式共用同一条管线，差异只在**输入源**与**默认预设/投递** —— 这正是 §3.2 归约的验证。

### 8.2 唤起时序（公理 A2 落地）

```
用户按 Alt+Q
   │
   ├─ 0ms      记录当前前台窗口句柄（ForegroundGuard.snapshot）
   ├─ ~10ms    显示【已预热】的面板（内容为空 / 显示"读取中…"）
   │             └── 用户已可感知"它来了" ← 感知延迟在此结束
   ├─ 异步     采集选中文本（Ctrl+C + 剪贴板还原，约 50~150ms）
   ├─ 异步     填充到输入框
   └─ 回车 → 流式回答 → 面板增量渲染
Esc / 失焦 → 关闭面板 → ForegroundGuard.restore()
```

**关键设计：面板常驻内存、隐藏待命，绝不每次重建。**
首次构建成本（Qt 控件树 ~50–100ms）必须发生在启动阶段（经 T3 的 `on_ui_ready`），
**不能发生在热键回调里**。

### 8.3 面板焦点策略（ADR-3）

| 场景 | Qt 设置 | 行为 |
|---|---|---|
| Ask / Translate（需输入） | `FramelessWindowHint \| WindowStaysOnTopHint \| Tool`，**不设** `WA_ShowWithoutActivating`，显示后调 `activateWindow()` | 面板获得键盘焦点 |
| Capture 结果展示（只读） | 额外设 `WA_ShowWithoutActivating` | 不抢焦点，不打断用户 |

关闭时统一 `ForegroundGuard.restore(hwnd)`。

### 8.4 桌宠的降级位置（公理 A1 落地）

（历史）桌宠曾从"交互入口"降为"**可选状态灯**"；v1.7.0 起桌宠已整体移除，这一段只作决策留痕：

| AI 事件 | 反馈（v1.7.0 起只剩气泡文案） | 是否影响功能 |
|---|---|---|
| 唤起 | （v1.7.0 起只弹气泡提示，无精灵图） | 否 |
| 思考 | （同上） | 否 |
| 回答中 | （同上） | 否 |
| 完成 | （同上） | 否 |

### 10.0.1 由实测确认的架构决策

1. **不需要为 AI 调用拆子进程**（确认 ADR-4 / ADR-7）。
   最重的 Markdown 全量重排策略下，主线程最大阻塞仅 34.8ms，远低于 50ms 阈值。
   `QTextDocument.setMarkdown()` 可直接用，**不必**自绘增量渲染。
   > 保留意见：`setMarkdown` 是 O(n) 全量重排，总成本 O(n²)。200 tokens 安全；
   > 若单次回答超过约 2000 tokens 需重新评估（可改为节流重排，如每 80ms 一次）。

2. **面板预热是硬需求**（确认公理 A2）。冷构建 63ms vs 预热唤起 5.8ms，差 10 倍。
   面板必须在 `on_ui_ready`（T3）阶段构建好并隐藏待命。

3. **`SetForegroundWindow` 必须配 `AttachThreadInput`**（验证 R12）。
   否则受 Windows 前台锁限制静默失败。

4. **新增红线：任何等待都不得用裸 `time.sleep()` 阻塞主线程。**
   S2 首轮失败即因此 —— 阻塞 Qt 事件循环导致目标窗口无法处理 WM_COPY。
   正确做法：泵事件循环 + 短睡眠（见 `spikes/s2_selection.py` 的 `_wait`）。

5. **依赖装在两个目录**：`Lib/`（requests/Crypto/urllib3）与 `Lib/site-packages/`
   （PySide6/pynput/pywin32）。`dev_bootstrap.py` 已同时挂载。

### 10.0.5 一次性冷启动开销清单（P2 性能整改的核心结论）

M1/M2 调试中最有价值的发现：**有若干"只贵一次"的操作，全都落在了用户第一次按热键的路径上。**

### 10.0.6 验证夹具方法论（踩坑记录）

端到端脚本最初**间歇性失败**（10 次里错 2–3 次），排查后确认**全部是夹具问题，不是产品缺陷**。
三条必须遵守的规则（已写入红线 18）：

1. **剔除夹具开销。** 合成按键的 `SendInput` 会阻塞调用线程；pynput 首次构造还要 71ms。
   不剔除的话，"最大阻塞"恒等于按键耗时。
   → `Heartbeat.mark_harness(t0, t1)` 记录时间窗，统计时跳过与之重叠的心跳间隔。
2. **剔除设计内等待。** `get_selected()` 曾有一段刻意的 ~250ms 等待（等目标应用落剪贴板）。
   这是设计，不是阻塞。→ 用 `mark_harness` 标记后单独作为数据报告。
   > **P2.8 已把这 250ms 消掉**：改为 30ms 窗口 + 8ms 轮询，实测 251ms → 32ms。
   > 这段等待不再是"设计内"的了。
3. **夹具也必须用 `AttachThreadInput` 抢前台。** Windows 前台锁会让 `activateWindow()` **静默失败**，
   于是目标窗口有时抢不到焦点 → `Ctrl+C` 取不到内容 →「替换原文」粘错窗口。
   → 复用产品自己的 `ForegroundGuard.restore()`，见 `spikes/_common.py::force_foreground()`。

> 教训：**端到端脚本的失败要先怀疑夹具。** 把"夹具开销"和"设计内等待"显式建模出来之后，
> 8/8 稳定通过，且测出来的数字（17ms）才真正反映产品行为。

### S4 — 同进程流式渲染是否卡顿

**要验证的假设**：Qt 主线程 + `requests` 流式解析 + 增量渲染 Markdown，是否会导致拖拽卡顿。

**最小实现**：

   （或本地起一个每 50ms 吐一个 token 的假服务）。

4. **同时**用鼠标疯狂拖拽桌宠窗口，观察是否掉帧。

若卡顿 → 需把 AI 调用拆到独立子进程，或改用自绘增量渲染。

### S1 — 全局热键能否与现有 InputMonitor 共存

**要验证的假设**：`RegisterHotKey` 与 `sensor/input_monitor.py` 的 pynput 监听不冲突。

**最小实现**：
```python
import ctypes, ctypes.wintypes
from PySide6.QtCore import QAbstractNativeEventFilter
from PySide6.QtWidgets import QApplication

MOD_ALT, WM_HOTKEY = 0x0001, 0x0312

class HotkeyFilter(QAbstractNativeEventFilter):
    def __init__(self, cb):
        super().__init__()
        self.cb = cb
    def nativeEventFilter(self, eventType, message):
        msg = ctypes.wintypes.MSG.from_address(int(message))
        if msg.message == WM_HOTKEY:
            self.cb(msg.wParam)
        return False, 0

app = QApplication([])
f = HotkeyFilter(lambda i: print("hotkey", i))
app.installNativeEventFilter(f)
ok = ctypes.windll.user32.RegisterHotKey(None, 1, MOD_ALT, ord("Q"))
print("registered:", bool(ok))
```

**同时**启动 `InputMonitor()`（`input_monitor.py:32`），保持 pynput 监听运行。

**判定标准**：
- `RegisterHotKey` 返回非 0；
- 连按 `Alt+Q` 100 次，回调触发 100 次；
- `InputMonitor.get_key_rate()` 仍在正常累计（未被热键吃掉按键）。

**已知坑**：
- `Alt+Q` 可能被其他软件占用 → 需要 `register` 失败时回退备选组合。
- 热键在**提权窗口**（UAC）聚焦时可能失效 → 这是 R1 风险的来源，需记录实测结论。
- 兜底方案：托盘菜单 + 双击桌宠（`TrayIcon`，`tray_icon.py:75`）。

**产出**：`spikes/s1_hotkey.py` + 实测结论（含提权窗口下的表现）。

### S3 — 面板低延迟唤起 + 焦点还原

**要验证的假设**：预热面板能做到 ≤150ms 可见，且关闭后能 100% 还原原窗口焦点。

**最小实现**：
1. 启动时创建 `AIPanel` 并 `hide()`（预热）。
2. 热键触发时：`guard.snapshot()` → `panel.show()` → 记录时间差。
3. `Esc` 时：`panel.hide()` → `guard.restore(hwnd)`。
4. 在 Chrome / 记事本 / VSCode 中分别测试，关闭后继续打字，看是否仍输入到原窗口。

**判定标准**：
- 唤起延迟 P95 ≤ 150ms（用 `time.perf_counter()` 打点，跑 50 次取分位）；
- 关闭后原窗口焦点还原率 100%；
- 多显示器下，面板出现在**鼠标所在屏幕**。

**已知坑（重要）**：
`win32gui.SetForegroundWindow` 受 Windows **前台锁**限制，直接调用常静默失败。
需用 `AttachThreadInput` 把当前线程挂到目标窗口线程上再设置，或发送
`ALT` 键的 `keybd_event` 解除锁。**这是本 spike 最可能踩的坑**。

**产出**：`spikes/s3_panel.py` + 延迟分位数据 + 焦点还原成功率。

### S2 — 选中文本方案在多应用是否可用

**要验证的假设**：`Ctrl+C + 读剪贴板 + 还原剪贴板` 方案在主流应用中可用。

**最小实现**：
1. 用 `QClipboard` 备份当前剪贴板（含所有 MIME 格式，用 `QMimeData`）。
2. 用 `pynput.keyboard.Controller` 发送 `ctrl+c`。
3. `time.sleep(0.15)` 后读剪贴板文本。
4. 还原备份的剪贴板。
5. 在 **Chrome / VSCode / 记事本 / Word / 微信** 中逐个测试。

**判定标准**：≥ 4/5 个应用成功取到选中文本，且**剪贴板内容被正确还原**。

**已知坑**：
- 管理员权限窗口 / 游戏内可能失效；
- 剪贴板被其他程序（如剪贴板管理器）抢占；
- 富文本应用还原时可能丢失格式 → 必须备份**全部** MIME 格式，不能只备份纯文本。

**产出**：`spikes/s2_selection.py` + 应用矩阵测试结果表。

## 11. 开发规范红线（违反即返工）

| # | 红线 | 依据 |
|---|---|---|
| 1 | **禁止在 Qt 主线程或 `event_bus` 回调中同步执行网络 / IO** | C3，`event_bus.py:165` |
| 2 | **AI 调用一律走线程池**（`QThreadPool` / `concurrent.futures` / `QThread`） | A4 |
| 3 | **`engine/ai/` 与 `native/` 不得 import PySide6**（`hotkey.py` 除外） | A1，可测性 |
| 4 | **禁止创建与标准库同名的顶层包**（`platform` / `types` / `code` / `token` …） | 会遮蔽标准库 |
| 5 | **插件内模块名必须带前缀**（`aiassist_*`），禁止 `config.py` / `logger.py` / `utils.py` | C1 |
| 6 | **AI 面板必须预热**，不得在热键回调里首次构建控件树 | A2 |
| 7 | **关闭面板必须还原前台焦点** | A5 |
| 8 | **新功能必须表达为"输入源 × 预设 × 投递"三元组**，否则提交架构评审 | A3 |
| 9 | **新增第三方依赖必须同步更新** `requirements.txt` + `SKILL.md` 的 `requires` + `PetDemo.spec` | C4 |
| 10 | **API 密钥禁止明文写入配置文件**，用 `keyring`（回退 Windows DPAPI） | 安全 |
| 11 | **禁止用裸 `time.sleep()` 阻塞主线程等待**；改用「泵事件循环 + 短睡眠」 | S2 实测踩坑 |
| 12 | **关闭面板必须还原前台焦点**，`SetForegroundWindow` 须配 `AttachThreadInput` | S3 实测（R12） |
| 13 | **SQLite 落库禁止在主线程 commit**；必须移入工作线程，并开 `WAL` + `synchronous=NORMAL` | M1 实测：主线程三次 commit **154ms** → 线程池 **2.8ms** |
| 14 | **面板预热必须真的画一次**（`processEvents` + `repaint`）；只 `show()`+`hide()` 会取消首绘 | M1 实测：冷绘制残留 145ms |
| 15 | **取选中文本必须在面板抢焦点之前**（先 `show_passive` 再 `get_selected` 再 `activate_for_input`） | M1 实测：顺序错则 `Ctrl+C` 复制到面板自身 |
| 16 | **有一次性冷启动开销的东西，必须在启动期预热**，不得留到首次热键响应。当前清单：`AIPanel`、`OverlaySelect`、pynput `Controller()`、剪贴板 | M2 实测：**Controller 构造 71ms / 首次剪贴板访问 88ms / 遮罩首绘 ~100ms**，三者叠加会让首次唤起卡 0.25 秒 |
| 17 | **截图只抓需要的区域**，不得先抓全屏再裁剪 | M2 实测：抓 1920×1080 全屏 **90ms** → 抓 320×200 区域 **3–5ms** |
| 18 | **验证脚本必须剔除「夹具开销」与「设计内等待」**，否则测的是夹具不是产品 | M1/M2 实测：不剔除时"最大阻塞"恒等于合成按键耗时或刻意等待时长，掩盖真实问题 |

## 13. 明确不做（范围护栏）

| 项 | 理由 |
|---|---|
| **防录屏隐身**（Pluely 核心卖点） | 与"功能优先"无关，投入产出比低 → 搁置 |
| **网络加速 / 代理** | 合规风险高 |
| **Live2D** | 需求已明确"表现形式不重要" → 直接排除 |
| **说话人分离 / 实时会议字幕** | 依赖云端付费 + 工程量最大，且非"查询/翻译"主场景 |
| **全格式文库 RAG** | 工程量远超收益，推迟至 v2 评估 |
| **为桌宠设计专属交互** | 违背 A1；桌宠只做被动反馈 |
| **替换 / 重构现有 6 个插件** | 与本次目标无关，避免扩大改动面 |
